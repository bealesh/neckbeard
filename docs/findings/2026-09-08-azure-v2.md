# V2 findings — first live run (Azure, serverless-containers, dev)

First deployment verification in project history: bellwether deployed to a real
Azure subscription via neckbeard's own bootstrap runbook and catalog, verified
over its public FQDN (`/healthz` ok, note persisted), updated via the manual
release flow, and torn down. Nine applies, ~2 hours, well under $2 of credits.

Every finding below was invisible to V0 (six lanes of fmt/validate/checkov/
kubeconform all green) — which is the design's whole argument for V2 (§12).

## What worked first try

- Bootstrap (state account, federated CI identities, role assignments, outputs)
  and the runbook's backend-wiring + CI-variable steps, verbatim.
- V1: authenticated plan over Entra-authed remote state, including the
  deployer's blob-data grant.
- Regeneration over a live workspace (region flip): 7 generated files updated,
  user files untouched, zero conflicts.
- The full platform: VNet, delegated subnets, private DNS, flexible server
  (Entra-only auth), vault, ACR, Container Apps env + apps, log analytics.

## Findings (fixed in this run)

1. **Key Vault cannot hold an empty secret value**, so "blank DATABASE_URL means
   in-memory" was unexpressible. Fixed app-side: bellwether TrimSpaces the env
   var; a whitespace secret means unset. Rule of thumb for the workload contract:
   reference apps must treat blank-ish secrets as absent.
2. **RBAC-mode Key Vault grants the operator nothing** — Owner is management
   plane only, so the runbook's "operators set secret values out-of-band" was
   impossible. Fixed: the secrets module now grants the deploying principal
   "Key Vault Secrets Officer" (org-managed operator groups replace this on
   Path F). Same class of fix as the bootstrap's state-blob deployer grant.
3. **Container Apps had no ACR pull path** — private images failed UNAUTHORIZED.
   Fixed: dedicated user-assigned pull identity + AcrPull wired from the
   registry module (and kubelet AcrPull on the AKS lane). A system-assigned
   identity cannot work here: its role assignment can only exist after the app,
   but the first private-image revision needs pull rights immediately.
4. **Subscriptions have per-region capability holes**: eastus/eastus2/westus2
   offered ZERO Postgres flexible-server SKUs to this (new, credit-funded)
   subscription — the API error is the unhelpful `'Version' should be in: []`.
   centralus/westus3/northeurope offered everything. TODO: `neckbeard configure`
   should probe capability (az postgres flexible-server list-skus equivalent)
   before a region is accepted.
5. **`count` on apply-time module outputs breaks fresh environments** (Invalid
   count argument). Fixed: registry wiring is unconditional — conditional-on-
   output patterns are banned in catalog modules.

## Findings (open — release-harness requirements)

6. **azurerm orphans resources on mid-apply failures**: several resources were
   created but never recorded in state when a later wait failed (VNet, DNS zone,
   role assignments, UAI, CA environment across passes). "Re-run apply and it
   continues" is FALSE for this class — recovery required six manual imports.
   Harness requirement: after any failed apply, reconcile ARM reality vs state
   (import-or-fail-loudly) before retrying. Runbook wording corrected mentally;
   file TODO to soften its idempotence claim for azure.
7. **Never recreate a same-named resource group promptly after destroy**: RG
   deletion is async, and its queued child-deletions ate resources created under
   the recreated RG (VNet vanished post-import; DNS zone flapped 404/exists).
   Harness requirement: unique per-run suffixes in names; never reuse an env
   name within the propagation window.
8. **Import UX**: one `tofu import` silently failed to persist in a chained
   shell (cause unclear — possibly the az-CLI subshell exit); always verify with
   `state list` after import. Harness: imports are followed by a state check.
9. **Entra-only Postgres vs password-style DATABASE_URL**: the azure postgres
   module (deliberately) has no password auth, so bellwether cannot yet reach it
   with a pgx DSN. The db leg of health verification is NOT EXERCISED on azure.
   Options to design: an Entra-token sidecar/refresher, enabling password auth
   with an operator-set password (never in state), or app-side azidentity token
   auth. Decision needed before the azure lane can claim the db check.
10. **Transient ARM 404s on fresh private DNS zones** (SOA read right after
    create) fail applies spuriously; the same zone read fine minutes later.
    Harness: retry-with-backoff on first-apply convergence.
